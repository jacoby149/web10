\begin{abstract}
ActivityPub (Mastodon) and ATProto (Bluesky) are running, non-cryptographic
social protocols---no blockchain, no gas fees, no wallet-gated feeds. But each
defines a rich protocol and then steps outside it: the server knows what a
post, a follow, or a like is, and special-cases them for performance. The
protocol is the spec; the implementation cheats around it.

We present \textbf{web10}, a user-owned-data platform whose node contains
\emph{no social primitives at all}---no feed, follow, post, group, or message
endpoint. The entire social application (feeds, groups, direct messages,
discovery) is composed, 100\%, from generic documents, groups, roles, and a
query engine: every database call goes through the same generic path, with no
platform-specific shortcut. Access is governed by fine-grained, revocable,
group/role-scoped contracts enforced at the query layer, so the generic path
stays secure at an index-lookup cost rather than a scan. And because that
generic path is fast enough, there is no reason to cheat: a feed that a naive
implementation loads with \textbf{267 network requests} loads in \textbf{one}
web10 query-engine call. A full social platform, built nothing but generic
queries, that runs at commercial grade---and a node general enough to host a
messaging app, a music app, or a shop without changing the platform.
\end{abstract}

\section{Introduction}
\label{sec:intro}

The dominant social platforms solve engagement extremely well and ownership
extremely poorly. A user's posts, messages, and relationships live in the
platform's database under the platform's access model. The user can adjust a
handful of visibility settings the platform chose to expose; they cannot
redefine who a ``friend'' or a ``member'' is, cannot contract access
per-service, and cannot take their data---let alone their audience---
elsewhere. When the platform changes its rules or goes away, the user's data
goes with it.

For a subset of users this is not an abstraction---it is a paycheck. Creators
and influencers build their income on their social graph: their audience is
the asset, and the platform that hosts it can deplatform them, shadowban their
reach, reprice their distribution, or take a larger cut, at will, with no
recourse. Trust in the platform is therefore a financial dependency, not a
preference. web10 removes that dependency by construction: delivery is
guaranteed by architecture (the feed is a query over the creator's own data,
not a platform-controlled ranking), and the audience is portable because it
lives under the creator's key, not the platform's.

Cloud infrastructure solved the authorization half of this problem long ago.
AWS IAM and its descendants give operators fine-grained, role-based,
service-scoped, revocable access control with cryptographic token
verification. But that model lives at the \emph{infrastructure} boundary: the
cloud provider owns the data plane, and the end user is invisible to it.
Nobody has brought the IAM model to the \emph{user} boundary of a social
platform---where the user, not the platform, is the principal that holds the
contracts.

The decentralized social web has real, running systems, and web10 builds on
that lineage rather than against it. \textbf{ActivityPub} (Mastodon) and
\textbf{ATProto} (Bluesky) are live, non-cryptographic protocols with large
user bases---deliberately no blockchain, no gas fees, no wallet-gated feeds,
which is the practical choice web10 shares. Their gap is the access model:
authorization stops at follow/block and collection-level control, with no
fine-grained group/role contracts and no request/approve/assign lifecycle, and
their data models are shaped to one app (a microblog or a post graph) rather
than a platform that hosts many. \textbf{Solid} goes further on ownership
(personal data stores, WebACL) but its container-level ACLs still lack a
group/role primitive, and its per-Pod storage makes a cross-user feed query
intractable, so its social applications never reached the scale of Mastodon or
Bluesky. \textbf{Cloud IAM} has exactly the permission language a social
platform needs---principals, roles, service-scoped operations, revocable
grants---but it lives at the infrastructure boundary, where the provider owns
the data and the end user is invisible.

What none of them do is \emph{live} in their protocol. Each defines rich
primitives and then bypasses them---the server special-cases posts, follows,
and likes for performance, so the protocol is a layer conformed to at the
edges, not the path every request takes. web10 does the opposite. Its node has
no social primitives, and its application never steps outside the generic
path: every database call---feed, follow, message, group, discovery---goes
through the same documents, groups, roles, and query engine, with no
platform-specific shortcut. And because that generic path is fast enough (a
267-request feed loads in one), there is no reason to cheat. That purity---and
the access model and columnar backend that make it safe and fast---is this
paper.

\textbf{web10} is a user-owned-data platform that makes that move. Every
user's data lives under their own key in a single columnar store; every access
decision is a check against two user-held contract layers; and the social
application (feeds, groups, direct messages, discovery) is composed 100\% from
generic primitives, with no app-specific surface in the node. This paper makes
three contributions:

\begin{enumerate}[leftmargin=*,nosep]
  \item \textbf{A fully generic node, used fully.} The node exposes only
  universal primitives---documents, groups, roles, services, and a query
  engine---and contains no social endpoints. The entire social application is
  composed from those primitives, every database call through the generic
  path, with no special-case fast path. The same node hosts a messaging app, a
  music app, or a shop without platform changes (\S\ref{sec:model},
  \S\ref{sec:eval}).
  \item \textbf{An access model that keeps the generic path safe}
  (\S\ref{sec:model}): an outer \emph{app trust} layer (per-origin, per-service
  operation grants) and an inner \emph{person trust} layer (group roles as
  per-service permission maps over three nested principal classes). Enforced at
  the query layer, the role check never touches the large document table---fine-
  grained control at an index-lookup cost, not a scan
  (\S\ref{sec:enforcement}).
  \item \textbf{Proof that pure-generic is fast enough} (\S\ref{sec:eval}): a
  running social platform whose feed---naively 267 network requests---loads in
  a single query-engine call, every row access-checked against the reader's
  role grants. The generic path needs no shortcut because it is already fast.
\end{enumerate}

The remainder of this paper: \S\ref{sec:model} defines the generic primitives
and the access model; \S\ref{sec:enforcement} shows how access is enforced over
one columnar table at zero scan penalty; \S\ref{sec:eval} presents the running
social platform---composed entirely of generic queries---and its 267-to-1 feed
as the demonstration; \S\ref{sec:related} positions web10 against the
decentralized social protocols and cloud IAM; \S\ref{sec:concl} concludes.

\section{The Access Model}
\label{sec:model}

\subsection{Two trust layers}

Every request in web10 names an \emph{app} (the calling origin), a
\emph{principal} (the acting user), a \emph{group} $G$, a \emph{service} $S$
(a data namespace such as \texttt{posts} or \texttt{comments}), and an
\emph{operation} $O$ (e.g.\ \texttt{readAll}, \texttt{create}). Authorization
asks two independent questions, and \emph{both} must pass:

\begin{center}
\small
\resizebox{\columnwidth}{!}{%
\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Layer} & \textbf{Question} \\
\midrule
App trust (outer wall)   & Can this \emph{app} perform $O$ on $S$? \\
Person trust (inner wall) & Can this \emph{principal}'s effective role in $G$ grant $O$ on $S$? \\
\bottomrule
\end{tabular}}
\end{center}

The app contract is \emph{infrastructure trust}: which origins may touch
which services, enforced by CORS in the browser and re-checked server-side on
every call. The group role is \emph{social trust}: which people may do what
inside a group. The split matters because the two layers change at different
rates and for different reasons---a user re-points an app's access without
leaving any group, and leaves a group without touching any app's access.

\subsection{Roles are per-service permission maps}

A role is a named bundle of per-service permissions---a map from service to
the operations it grants:

\begin{lstlisting}[style=json]
{ "name": "editor",
  "permissions": {
    "posts":    ["readAll", "create", "updateOwn"],
    "comments": ["readAll"]
  } }
\end{lstlisting}

The map \emph{is} the scope. \texttt{'*'} wildcards all document services; a
reserved key \texttt{'group'} carries \emph{structural} operations on the
group itself (\texttt{manageRoles}, \texttt{assignRoles},
\texttt{deleteGroup}, join/member operations), while \emph{content}
operations---including moderation such as \texttt{hideAll}---live under the
service key, because they act on documents, not on the group's shape.

Two properties keep the model small. First, the role map is the
\emph{same shape} as the app-contract permission object: there is one
permission language across both trust layers. Second, a person holds
\emph{exactly one role} per group; the per-service map makes a single role
fully expressive over any (principal, service, operation) matrix, so there is
no multi-role stacking to reason about. Roles are generic---a group defines
whatever roles fit its purpose (\texttt{owner}, \texttt{moderator},
\texttt{page-curator}, \texttt{member}, or \texttt{dj}, \texttt{listener})---
and the platform never names them.

\subsection{Principal classes and effective permissions}

Access is granted to \emph{principals}, of which there are three nested
classes, broadest to narrowest:

\begin{center}
\small
\begin{tabular}{ll}
\toprule
\textbf{Class} & \textbf{Who} \\
\midrule
\texttt{anyone}        & every request, signed in or not \\
\texttt{authenticated} & any valid token (any user, member or not) \\
\texttt{member}        & holds a member row in this group \\
\bottomrule
\end{tabular}
\end{center}

The classes are \emph{reserved keys in the member table}---no separate
visibility table exists. A group grants a class a role by storing a member
row for the reserved key:

\begin{lstlisting}[style=sql]
group_members:
  (G, 'anyone',        'reader')    -- the group is public
  (G, 'authenticated', 'reader')    -- signed-in users can read
  (G, 'bob',           'moderator') -- bob moderates
  (G, 'alice',         'owner')     -- alice owns
\end{lstlisting}

A principal's \emph{effective} permissions in a group are the union of the
permission maps of every class they belong to:

\begin{center}
\small
$\mathrm{effective}(P, G) \;=\; \mathrm{grant}(G,\ \texttt{anyone})$\\
$\quad \cup\ \big(P \in \texttt{authenticated} \;?\; \mathrm{grant}(G,\ \texttt{authenticated}) : \emptyset\big)$\\
$\quad \cup\ \big(P \in \texttt{member}(G) \;?\; \mathrm{grant}(G,\ \mathrm{role}(P)) : \emptyset\big)$
\end{center}

The nesting buys a monotonicity invariant for free: a member always sees at
least what a signed-in stranger sees, who always sees at least what a
signed-out visitor sees. The model cannot express the inversion.

\subsection{Publicness is a grant, not a flag}

There is no \texttt{visibility} column. ``Make my group public'' is the act
of granting \texttt{readAll} to \texttt{anyone}; ``signed-in only'' grants it
to \texttt{authenticated}; ``private'' grants it to member roles only. Join
policy is orthogonal: it controls how a human \emph{becomes} a member (open,
request, invite-only) and says nothing about what a non-member bystander can
see. A group can be invite-only to join and still publicly readable---the
discovery board is exactly that.

This is the sense in which web10 brings IAM to the front: the operations a
cloud operator would express as policies---\emph{principal class, service,
operation, grant}---are the operations an \emph{end user} expresses about
their own data, with the same revocability (a grant is a row; removing it is
a tombstone that takes effect on the next read).

\section{Enforcement at the Query Layer}
\label{sec:enforcement}

\subsection{One columnar table}

All structured user content lives in a single ClickHouse table, keyed by
\texttt{(author\_key, doc\_id)}; large binary objects (media) live in object
storage and are \emph{referenced} from this table (\S\ref{sec:enforcement}):

\begin{lstlisting}[style=sql]
CREATE TABLE documents (
    doc_id          String,
    author_key      String,
    collection_name String,   -- the service: 'posts', 'comments', ...
    body            String,   -- JSON
    tags            Array(String),
    created_at      DateTime64(3),
    updated_at      DateTime64(3),
    deleted         UInt8 DEFAULT 0
) ENGINE = ReplacingMergeTree(updated_at)
ORDER BY (author_key, doc_id);
\end{lstlisting}

Updates are inserts with a higher \texttt{updated\_at} (the engine keeps the
latest version); deletes are tombstone rows filtered at read time. Documents
attach to groups through a small mapping table, and groups carry their
contracts and members in two more small tables. Content is one wide
columnar table; \emph{access is a handful of narrow metadata tables}.

\subsection{The role check never touches the document table}

The read path is the heart of the design:

\begin{enumerate}[leftmargin=*,nosep]
  \item \textbf{Resolve.} Look up the reader's rows in
  \texttt{group\_members} (including the reserved principal-class rows) and
  the role maps in \texttt{group\_contracts}. These are small, hot, and
  indexed by their primary keys.
  \item \textbf{Compute.} For the requested service, compute the set of group
  identifiers whose effective role grants \texttt{readAll} to the reader.
  \item \textbf{Scan.} Run the columnar \texttt{documents} scan exactly as it
  always would, with the cleared-group list as an ordinary filter, unioned
  with the reader's own \texttt{author\_key}.
\end{enumerate}

The authorization decision is therefore an index lookup into small metadata
tables, not a per-document check inside the scan. The scan stays a scan. This
is the ``zero scan-time penalty'' property: fine-grained, per-group,
per-service control costs the same as the coarsest possible filter, because
it \emph{is} a filter list computed once per query.

\subsection{The same invariant on every path}

The enforcement rule is uniform: \emph{no query returns documents for an
\texttt{author\_key} the token does not own, unless group membership grants
access} (invariant I3). Every read path---group feed, read-by-id, directory
search---applies the identical principal-class gate, and the write side is
gated the same way, so a bystander cannot attach content to a group they
cannot write. A conformance suite of permission-matrix cases (including
replayed-exploit denials) enforces the invariants mechanically; the full
suite results appear in the extended version.

\subsection{Two data dimensions, one access model}

web10 stores user data in two places: structured rows in the columnar store,
and large binary objects (images, audio, video) in object storage (MinIO/S3
API). Both are governed by the \emph{same} group/role/I3 model, because the
permission gate for an object is a \emph{document}, not the file.

A media object is referenced by a row in \texttt{documents} (a
\texttt{media\_refs} array or a \texttt{minio} leaf carrying the object key).
Access to the bytes is therefore derived from access to that document: the
node never hands out a permanent URL. For single-file objects (images, audio,
documents) it mints a \emph{presigned URL} with a short TTL---the browser
fetches directly from object storage, no middleware hop, and a shared link
dies when the URL expires. The gate is the document read that produced the
URL; a reader who cannot read the document never gets a URL at all.

Video streaming is the one case where a per-object presigned URL breaks (an
HLS video is 100+ small segments fetched continuously over minutes). There the
node instead signs a manifest bound to \emph{(reader, document, prefix)} and
validates a short-lived JWT on every segment; on each manifest (re)fetch it
re-runs the same \texttt{can\_view\_doc} check the read path uses, so a
removed or blocked reader loses the stream within one signature TTL. The
re-check answers ``can this reader see this?'' exactly the way the document
read did---it is revocation working within a TTL, not a second, stricter
model.

The point for the architecture: adding a second storage dimension does not add
a second access model. Objects are governed through the documents that
reference them, so the group/role contracts and the I3 invariant apply to a
creator's video the same way they apply to their post. This is also why the
feed's single request can carry resolved media: the query engine's prepare
pass mints the per-row object URLs (presigned, or signed manifests for HLS)
after the SELECT, reusing the read path's access checks verbatim.

\section{A Running Social Platform}
\label{sec:eval}

The strongest evidence for the model is not a benchmark but a product: web10
runs a complete social application---feeds, groups, direct messages, and
discovery---entirely on the primitives of \S\ref{sec:model} and
\S\ref{sec:enforcement}, with no app-specific surface in the node (D60). This
is the commercial-grade execution of user-owned social data that protocol-
first systems such as Solid proposed but did not ship. We highlight the feed,
because it is the workload that most stresses the design: a real social feed
must be large, tunable, and access-controlled simultaneously.

\subsection{The feed as a query}

A naive social feed is a stack of N+1 fan-outs: one call per author profile,
per post's media, per avatar, per engagement count. Measured on web10's first
feed implementation, loading a single page issued \textbf{267 network
requests}. The fix was not more batching on a bespoke endpoint---it was making
the feed an ordinary query over the columnar store, so that one request returns
the whole page. Three properties hold at once in that single call:

\begin{enumerate}[leftmargin=*,nosep]
  \item \textbf{It collapses the fan-out.} The 267 requests become
  \textbf{one}: a single query-engine call returns the full page---posts with
  resolved media and streaming manifests, exact like/comment counts, author
  profiles and avatars, and attached ads---as one envelope, keyset-cursor
  paged. The engine's \emph{prepare pass} mints the per-row capabilities
  (presigned media URLs, ad attachment, author face) after the SELECT, reusing
  the read path verbatim, so the one request carries everything the old 267 did.
  \item \textbf{It is fully user-gated.} Every row in that single response
  passed the access model on its way out: the query's boundary CTEs apply
  invariant I3 (no document for an \texttt{author\_key} the token does not own)
  plus the reader's effective group/role grants (\S\ref{sec:model}). The result
  is not an arbitrary batch; it is exactly the set the reader's role clears.
  Fine-grained social access and a large feed coexist in one query---the
  conjunction that is this paper's core claim.
  \item \textbf{It is tunable---and generic.} The feed's shape---what it
  contains, how it is ranked and filtered---is a query the \emph{application}
  writes, not logic hardcoded in the node. A different query is a different
  feed. Crucially, this goes through the \emph{general} query engine, not a
  social-specific endpoint: the node never learns what a ``feed'' is (D60). Any
  app can issue its own ranked, resolved, access-checked read the same way; the
  social feed is the reference example.
\end{enumerate}

This is the ``because of the columnar backend'' point made concrete: Solid's
per-Pod architecture makes a cross-user feed query intractable (each Pod is a
separate server), so its social applications remain hypothetical. web10's
single table makes the feed a first-class, tunable query---267 requests reduced
to 1---while the access model stays a filter list with zero scan penalty.

\subsection{Durability and extensibility}

Because the node exposes only universal primitives and the access model is a
per-service role map, the social app is not a one-off demo---it is the hardest
instance of a general pattern. The same substrate supports other app shapes
(a messaging app, a music app, a shop) by defining new services and roles
over the same tables, with no node changes. The social platform demonstrates
that the model carries a demanding, real workload; extensibility to other
apps follows from the same genericity.

\section{Related Work}
\label{sec:related}

\textbf{Decentralized social data.} web10 is in the lineage of the running,
non-cryptographic decentralized social protocols and builds on it.
ActivityPub~\cite{activitypub} (Mastodon) and
ATProto~\cite{atproto} are live systems with large user bases; both are
deliberately blockchain-free---no gas fees, no wallet-gated feeds---the same
practical stance web10 takes. Solid~\cite{solid} goes furthest on ownership
(personal data stores, WebACL) and has produced a body of work on building
social applications over them. All four establish that a user can \emph{own}
their data without a ledger.

The gap web10 addresses is authorization granularity and generality.
ActivityPub and ATProto authorize at the level of follows and collection-level
visibility; neither has fine-grained group/role contracts or a request
$\rightarrow$ approve $\rightarrow$ assign-role lifecycle, and each data model
is shaped to one app. Solid's WebACL answers ``who may read or write this
container?''---a coarse, resource-level question---with no first-class
\emph{group} primitive carrying \emph{roles}. web10's contribution is exactly
this missing layer: access as \emph{person $\rightarrow$ role $\rightarrow$
per-service operations}, granted \emph{inside} a group through an explicit
join-request and approval flow, where a role is a map from data service to the
operations it grants (\S\ref{sec:model}). On top of that, web10's node is
generic---its primitives support arbitrary app shapes, not just the one social
app each earlier protocol was built around---and it does so on a running
platform whose feed collapses 267 requests into one.

\textbf{Cloud IAM.} AWS IAM~\cite{awsiam} and the RBAC/ABAC
literature~\cite{rbac} define the permission language web10 reuses at the
user boundary: principals, roles, service-scoped operations, revocable
grants. The move in this paper is directional---the same policy shape, held
by the end user about their own data, enforced by the data layer rather than
a control plane.

\textbf{Multi-tenant isolation.} The database literature on tenant
isolation---schema-per-tenant, database-per-tenant, and row-level
security~\cite{rls}---is the closest systems ancestor. web10's key-space
per user is tenant-per-end-user taken to its limit: the tenant is the
\emph{end user}, and the isolation is expressed as the query's
\texttt{author\_key} filter plus group-grant list rather than a physical
boundary. The cost tradeoff of that choice is measured in the extended
version.

%=============================================================================
\section{Conclusion}
\label{sec:concl}

web10 brings the cloud IAM permission model---principal classes, roles,
service-scoped operations, revocable grants---to the user boundary of a
social data platform, and enforces it at the query layer of a single
columnar store so that fine-grained authorization costs an index lookup, not
a scan. We demonstrate the model in a running social platform whose feed is a
tunable query that collapses 267 network requests into one, every row access-
checked---the commercial-grade execution of user-owned social data that
protocol-first systems proposed but did not ship. The extended version adds
scale and latency figures and the cost comparison against row-level-security
baselines.
